
# Architecture Overview

## Data Sources

The platform supports multiple data sources for flexibility in development and production environments:

1. **Production Data**: Raw JSON files for orders, customer master data, and product catalogs ingested from external systems.

2. **Synthetic Data**: Deterministic payloads generated by scripts in `infra/seed/` for local development and testing. These synthetic generators produce realistic data that flows through the same ETL pipelines as production data, ensuring consistency and reliability.

The complete data flow from seed generation to ETL stage/load involves:
- Seed generation: Scripts in `infra/seed/` create synthetic CSV and JSON files based on configuration in `seed_config.yaml`.
- ETL Extract: Data is extracted from seed files and loaded into staging tables (`stg` schema) with payload hashing for deduplication.
- ETL Transform/Load: Data is transformed, deduplicated using SHA-256 hashes, and loaded into the warehouse (`dw` schema) dimensions and facts.
- Audit: All ETL operations are logged in the `meta.etl_audit` table for tracking and monitoring.

## CDC & Incremental Loads

Incremental jobs rely on two metadata tables to guarantee idempotency and SCD-1 semantics:

- `meta.cdc_state` stores the watermark (last updated_at/transaction_ts) processed for each entity and contains details about the last run (row count, strategy used).
- `meta.dim_fingerprint` stores SHA-256 fingerprints for SCD-1 dimensions (customer_nk, sku) to ensure updates are only executed when values change.

The incremental flow is:
1. Read new files (or payloads from stg.*).
2. Normalize and validate data, determining record_ts and canonical fingerprint.
3. For **watermark** strategy, only process records with record_ts greater than meta.cdc_state.watermark_ts (adjusted with offset).
4. For **hash** strategy, compare fingerprints and execute ON CONFLICT DO UPDATE only when values change.
5. meta.cdc_state is updated at the end of the run to allow safe incremental resume.

The diagram in `docs/diagrams/etl_flow.mmd` shows both batch and incremental flows, including fingerprint and watermark preservation.

## Streaming

The platform includes a lightweight streaming system for real-time data processing, complementing batch and incremental ETL. This system is designed for low-volume, low-latency scenarios without replacing traditional ETL.

### Key Components:

1. **Kafka Consumer**: Reads messages from Kafka topics (orders, customers, products) using a consumer group for load balancing.
   - Default Kafka broker: `redpanda:9092` in Docker, `localhost:9092` for local dev
   - Topics: orders, customers, products
   - Consumer group: streaming_group

2. **File Tail Reader**: For local development, reads new lines from a JSON file (one message per line) using tailing.
   - Usage: `python -m backend.app.streaming.file_orders_worker watch /path/to/orders.json`

3. **Orders Worker**: Processes order batches, inserting directly into fact_sales using bulk operations.
   - Batch size: 100 (configurable)
   - Poll timeout: 1000ms (configurable)

### Service Ports

When running with Docker Compose:
- PostgreSQL: 5432
- Redis: 6379
- MinIO: 9000 (API), 9001 (Console)
- Redpanda (Kafka): 9092
- API: 8000
- Prometheus: 9090
- Grafana: 3000

For local development, all services use the same ports but connect to `localhost` instead of service names.

### Environment Configuration

Key environment variables (see `.env.example` for full list):
```bash
# Database
DATABASE_HOST=localhost  # Use 'postgres' in Docker
DATABASE_PORT=5432

# Streaming
STREAMING_KAFKA_BOOTSTRAP_SERVERS=localhost:9092  # Use 'redpanda:9092' in Docker
STREAMING_KAFKA_GROUP_ID=streaming_group
STREAMING_BATCH_SIZE=100
```

### Flow Architecture

1. Worker connects to data source (Kafka or file)
2. Reads messages in configurable batches (default 100)
3. For each batch, executes bulk insert into fact_sales
4. Logs errors but implements simple retry logic

### Limitations

- No deduplication (assumes unique data)
- No dimension updates (dim_customer, dim_product must be populated via batch/incremental ETL)
- No audit logging in meta.etl_audit
- Potential duplicates if same message processed by multiple consumers
- Simple retry logic, no dead letter queue

### Usage

Local Development:
```bash
# Watch file for new messages
python -m backend.app.streaming.file_orders_worker watch /path/to/orders.json

# One-time file processing
python -m backend.app.streaming.file_orders_worker tail /path/to/orders.json
```

Production:
- Kafka worker runs as a separate service via Docker Compose
- Configure through environment variables
- Monitor via Prometheus/Grafana dashboards
